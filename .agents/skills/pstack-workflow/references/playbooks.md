# pstack Playbooks 执行清单（Antigravity 版）

根据任务类型选择对应的 Playbook，将关键步骤直接作为当前任务的执行清单，逐步打勾推进，禁止跳步。

---

## 1. Bug Fix（科学排障流）

1. **锁定现象与复现条件**：明确期望行为、实际行为、触发输入与环境。
2. **取证定位入口**：使用 `batch_search` / `codegraph` 找到实际执行路径，阅读真实代码，禁止猜测。
3. **先复现，再动手**：运行现有测试、编写最小复现单测，或用 `run_command` / `browser` 稳定复现故障。
4. **定位根因**：区分「表象」与「根因」（例如空指针往往源于上游状态未初始化，而不是缺一个 `if != nil`）。
5. **最小化修复**：应用 `Laziness Protocol`，只改根因所需的最小范围。
6. **回归证明**：先确认刚才失败的复现用例现在通过，再跑关联模块测试与静态检查。
7. **防复发判断**：如果同类错误容易再次发生，补充回归测试或建议新增 lint/类型约束。

---

## 2. Feature（功能开发流）

1. **澄清边界与验收标准**：若需求存在歧义或高代价取舍，先向用户确认，不擅自假设。
2. **域建模与接口先行（`/architect`）**：先确定数据结构、类型定义、错误契约与模块边界（检查影响面 blast radius）。
3. **拆分为可独立验证的单元**：将大改动拆为若干小步，每步完成后可独立编译并验证。
4. **小步实现**：复用现有模式与工具函数，不造多余抽象层。
5. **行为测试（Test Behavior）**：围绕核心正常路径 + 关键边界/失败路径编写行为级测试。
6. **真实运行验证（Prove It Works）**：实际跑通端到端路径（CLI 命令、HTTP 请求或 `browser` 子代理交互），确认数据流转与持久化符合预期。
7. **自查与清理（Deslop）**：审查 `git diff`，清理多余注释、未用导入和临时代码。

---

## 3. Refactor（安全重构流）

1. **建立行为护栏**：重构前先确认目标代码有覆盖关键行为的测试；若缺失，先补基线测试并确认通过。
2. **先减后增**：优先删除死代码、重复分支和无用抽象，再做结构提炼。
3. **严格隔离行为变更**：重构本身不混入新功能；若必须改行为，拆分独立步骤。
4. **小步验证**：每完成一个结构迁移点即跑一次测试/类型检查，避免大面积改崩难以回溯。
5. **前后对照**：确保所有既有测试与外部契约保持兼容。

---

## 4. Investigate（只读调研流：`how` / `why`）

> 严格只读：不修改任何业务代码文件。

- **`how`（它现在怎么跑）**：
  1. 找到真实入口点（路由、CLI、定时任务、事件订阅等）。
  2. 沿真实调用链逐步追踪，记录关键文件与行号、状态变更点、外部依赖。
  3. 用清晰链路说明实际行为，区分「代码实证」与「推断」。
- **`why`（当初为什么这么写）**：
  1. 用 `batch_search` 的 `git` 查询（如 `git log -S` / `git blame` / `git log -p`）查看引入提交与历史演化。
  2. 结合相关文档/注释/Issue 线索还原设计约束与历史权衡，不凭空编造动机。

---

## 5. Architect（架构与边界设计流）

1. **现状盘点**：查清现有模块划分、依赖方向与已有的约定模式。
2. **给出最小可行结构**：画出核心数据结构、接口签名、状态机与依赖流向（禁止循环依赖与跨层直调）。
3. **列出取舍与风险**：说明为什么不选更复杂的方案，标注影响面（blast radius）与回滚/兼容策略。
4. **拆解验收里程碑**：给出按可验证单元排列的实施顺序，待确认后再进入编码。

---

## 6. Interrogate & Deslop（对抗式审查与去水）

1. **拉取完整变更**：执行 `git status` 和 `git diff`，仅基于真实 diff 审查。
2. **对抗式拷问（Interrogate）**：逐项挑战改动——
   - 边界条件（空值、并发、重试/幂等、超时、权限）是否被击穿？
   - 是否悄悄改变了既有契约或破坏了调用方？
   - 错误是否被吞掉或掩盖了根因？
   - 测试是否真的验证了行为，还是只在 mock 自己？
3. **去水清理（Deslop）**：
   - 删除只复述代码的废话注释。
   - 删除仅服务于单次调用的过度封装。
   - 精简无意义的防御性代码和死分支。
4. **分级输出**：按「必须修复（阻塞） / 建议优化 / 可忽略」输出带文件行号的具体证据，不盲目套改。

---

## 7. Parallel（并行探索 `arena` / 分片协同 `swarm`）

仅在**单兵验证闭环已建立**且任务收益大于协调成本时启用：

- **`arena`（多方案择优）**：面对高不确定性设计分叉，用 `invoke_subagent`（`Workspace: "branch"` 或 `"share"`）起 2~3 个独立子代理分别实现不同方案 → 对比可维护性、复杂度与实测结果 → 取最优底座融合精华，丢弃其余分支。
- **`swarm`（独立切片并行）**：面对多个互不冲突的子模块/文件切片，使用 `swarm` 工具（写作者用 `workspace: "share"`，审查/验证者用 `inherit`）分片推进，汇总后在主工作区做统一回归验证。
